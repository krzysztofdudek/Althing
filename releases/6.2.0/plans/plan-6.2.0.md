## 7. Design sections

### 7.1 C# reachability (014, 075 b; how 164, 177, 185, 188 relate)

**The rule.** C# binds a name only to declarations in the compilation itself or in assemblies it references. Runes reads the syntax of one file at a time and, until now, offered every in-repository declaration of a name as a candidate, so an extension method or a type in a project the caller cannot reference produced a false, unsuppressible `relation-undeclared-dependency` (and could force a `structural-cycle`), and the two implicit `Program` classes of an ASP.NET solution silenced the one real edge. The fix filters candidates by the project reference graph, in the resolver, so both consumers get it from one place (the earlier plans' D7 a; filtering in Yggdrasil's pass would leave Grain out).

**The builder** (new, `buildCsharpReachability(projectRoot, csFiles, options?: { files?: FileView }): Reachability`). Projects: every `*.csproj` the view lists (dot-directories, `bin/`, `obj/`, `node_modules/` skipped); the project of a `.cs` file is the nearest ancestor directory holding a `.csproj`, the rule `buildCsharpProjectScopes` already uses (several `.csproj` in one directory are one project). For each project the reference facts are read from its `.csproj` files and from every ancestor `Directory.Build.props` and `Directory.Build.targets` (a union: MSBuild imports the nearest, which commonly imports the next one up through `GetPathOfFileAbove`; reading them all can only add reach):

- `<ProjectReference Include="…">`: a path relative to the declaring file; `$(MSBuildThisFileDirectory)` and `$(MSBuildProjectDirectory)` are substituted; a wildcard is matched against the listed `.csproj` files; any other `$(…)` cannot be resolved, so the declaring project is **open** (it reaches everything).
- `<Reference Include="Name, Version=…">` with or without `<HintPath>`: the in-repository project whose `<AssemblyName>` (default: the `.csproj` file stem) equals `Name` or the HintPath's dll stem (jellyfin's `fuzz/*/Program.cs` case); no such project means an external assembly, ignored.
- `<PackageReference Include="Id">` whose `Id` equals an in-repository project's `<PackageId>` or assembly name: a reference (a repository that consumes its own packages).
- `<Compile Include>` naming files outside the project's directory, or an `<Import>` of a `.projitems` shared project: the project is **open**.
- Conditions are read, never evaluated (every branch counts). Project references are transitive, as in SDK-style projects (`PrivateAssets` and `DisableTransitiveProjectReferences` are not read: only more reach).

`reach(fromFile, targetFile)` answers `'same'` (one project), `'reachable'` (the target's project is in the caller's closure, the caller's project is open, or either file is not C# or lies under no project: no facts, no restriction), or `'unreachable'`.

**In the resolver** (`ResolverDeps.reach?`, optional; absent = today's behaviour exactly): on the symbol axis, before the owner count, a hint's definers lose every `'unreachable'` file; if any remaining definer is `'same'`, only the `'same'` ones stay (C#'s CS0436: a type of the compilation wins over a referenced assembly's type of the same name). For `Program`, whose explicit key and implicit top-level key (`<Program>$`, `csharp.mts:225`) are one name to the compiler, the two candidates are treated as one set when `reach` is given, then filtered the same way; without `reach` the 1.0.1 order (explicit outranks implicit) stays. The filter applies to every symbol hint, extension-method candidates included, and to `resolveFile` and `classify` alike (they share `hintFiles`). The path axis is untouched.

**What each issue gets.** 014: cases 1 and 2 lose their false edges (the target project is unreachable), case 3 too when the inherited member's same-named type lives in an unreachable project; a same-named type inside a reachable project is still a false edge from a one-file reading, kept as a documented known limit with a case. 075 b: the referenced project's implicit `Program` is the only reachable definer, so the edge appears; with both entry points referenced, silence (CS0433). 164: `ILogger<Program>` in a project with its own `Program` binds to itself (same-compilation preference), in a project without a reference to the partial `Program` gives nothing. **177, 185 and the C# part of 188 are extraction**, not resolution: they decide which candidates exist (`csharp.mts`, rev 6, package R3); R2 decides which of them a caller can see. The two packages are independent and file-disjoint; R2's evidence runs are repeated after R3 merges if R3 lands first, since new candidates pass through the new filter.

**Fail-open, on purpose.** Every unknown (an unresolvable property, a shared project, a linked file, no project file at all, a Unity repository whose `.csproj` files are git-ignored and so absent from the view) makes the filter allow more, never less, so the worst case is the 1.0.1 answer. The jellyfin, eShop and CleanArchitecture comparisons (no real edge lost) are the acceptance.

### 7.2 The commit-tree file view (235), and how Grain 099/106 and Yggdrasil 004/010 switch to it

**The problem.** Every resolver reads the disk: `existsSync`/`statSync`/`readdirSync`/`readFileSync` in `resolve-path.mts`, `repo-layout.mts`, `exact-case.mts`, `typescript-resolve.mts` and `csharp-project.mts`. So an untracked or ignored file (build output, a generated config, an installed package) decides where an import lands, and the same commit gets different edges on different machines (010). `isExcluded` patched part of it, per resolver.

**The interface** (exported from `relations`):

```ts
export interface FileView {
  exists(path: string): boolean;        // a file or a directory; '' is the root
  isFile(path: string): boolean;
  isDirectory(path: string): boolean;
  list(dir: string): ReadonlyArray<{ name: string; kind: 'file' | 'dir' }> | undefined;
  read(path: string): string | undefined;   // UTF-8 text, BOM kept for the parsers to strip
}
export function listedFileView(paths: Iterable<string>, read: (path: string) => string | undefined): FileView;
export interface ResolvePathOptions { files?: FileView; onDiagnostic?: (d: RelationDiagnostic) => void }
// makeResolvePathToFile(projectRoot, ownerOf?, isExcluded?, options?: ResolvePathOptions)
// buildCsharpProjectScopes(projectRoot, files, options?: { files?: FileView })
// buildCsharpReachability(projectRoot, csFiles, options?: { files?: FileView })
```

Paths are POSIX and relative to `projectRoot`, the base every specifier and owner already uses. `listedFileView` takes the file list (directories are implied by it; names are exact by construction, so the exact-case probe is not needed) and a reader; anything not listed does not exist: no symlinks unless listed, no `node_modules`, no build output. The default, when no view is passed, is an internal disk view that reproduces 1.0.1 byte for byte (exact-case check included), so a consumer that does not adopt the option sees no change. `isExcluded` keeps its meaning on top of the view (nested projects, `coverage.excluded`). Runes spawns no git: the consumer supplies the list and the reader, which keeps Runes free of process and repository concerns and lets each consumer choose what "the commit" means for it.

**What each consumer passes.** Grain's index is a function of HEAD, so G9 passes the HEAD tree (`git ls-tree -r -z HEAD`, modes 120000 and 160000 dropped, reads through a lazy `git cat-file --batch`); that replaces the materialised tree 099/106 introduced (`engine/commit-tree.mjs`, about 2.5 s per refresh on typeorm) for resolution, and `measure`'s `git archive` snapshot (`engine/measure.mjs:54-74`, which honoured `export-ignore` and wrote inside `.grain/`). Yggdrasil judges the working tree that is about to be committed (the pre-commit hook) and the checked-out commit in CI, so Y5 passes, per D9, the files git would commit: tracked files plus untracked files no ignore rule matches (the 004/068 machinery already computes `listIgnoredUntrackedPaths`), read from disk. In CI both readings are the commit; locally, a `dist/` built and ignored is invisible to both. That closes 010's determinism half for Yggdrasil (resolution and, through `guardOwnerIndex`, ownership), which 004/068 did not: the walk honours ignores, but the resolver and the owner index still saw ignored files.

**Tests that hold it.** The whole catalogue resolved through both views must be identical (section 2, R1); 010's three layouts give one verdict before and after a build (Y5); 099's sparse clone and 106's dirty tsconfig keep their answers through the view (G9); the corpus goldens do not move in R1.

### 7.3 The diagnostics callback (234)

```ts
export interface RelationDiagnostic { code: string; file: string; line?: number; column?: number; message: string }
```

Delivered through `ResolvePathOptions.onDiagnostic`, synchronously, at most once per `(code, file)` per resolver instance, only when resolution actually consults the file (so a broken config nothing imports through stays quiet). Codes are stable, as error codes are in 1.x (`docs/api.md` lists them: `config-unreadable` from R1, `package-entry-missing` from R5); `message` and `line`/`column` are best effort and not part of the promise; `code` is a `string`, not a union, so adding a code in a later minor does not break an exhaustive `switch`. `config-unreadable` covers the JSON family Runes parses (`tsconfig*.json`, `jsconfig*.json`, `package.json`, `composer.json`, `compile_commands.json`) and a `pnpm-workspace.yaml` whose `packages:` cannot be read; the position is mapped from `parseJsonc`'s stripped text back to the original. Behaviour is unchanged: an unreadable config still reads as `'unknown'` (silence for the specifiers it governs); the callback only makes the silence visible. **Yggdrasil** (Y5) turns each into a non-blocking warning, `relation-config-unreadable` and `relation-package-entry-missing`, registered in the code registry with stage `relations` beside `relation-file-binary`. **Grain** (G9) discloses them in `relStages.diagnostics`, in the export (schema note) and as one line of the propose report. Neither consumer blocks on them: a broken config is a fact about the repository, not a violation.

### 7.4 Java same-package binding (233) and its Yggdrasil "Before you upgrade"

**What changes.** Java makes a top-level type visible by simple name to every file of its package without an import (JLS §7.6); a test in the main class's package (`src/test/java/com/a/OwnerTest.java` using `Owner`) is the usual case. Runes 1.0.x emitted nothing for it (the catalogue case `java-same-package-no-import-silence` called it forbidden, for fear of JLS §6.4/§6.5.5 shadowing), so neither tool saw a test → main dependency, and Grain carried its own binding (`javaSamePackageRefs`) which 6.1.1 narrowed to the same directory. The owner chose the Runes binding (D8 a) for a minor with a CHANGELOG warning; 6.2.0 is that minor.

**How the extractor emits** (R4, `java.mts`, rev 4). At each simple type name in a type position (`type_identifier`: declarations, generic arguments, `extends`/`implements`/`throws`, casts, `instanceof`, `new Foo()`, `catch`, `Foo.class`, annotations) and at a capitalised receiver in an expression (`Foo.m()`, `Foo.X`, `Foo::m`), unless shadowed, a symbol hint `<package>.<Name>` resolved through the shared JVM namespace (so a Kotlin class of the package counts too, and the owner-collapse rule silences a name declared in two owners). Shadowing, in JLS order: a type parameter in scope, a type declared in the file (nested types included), a local class: nothing is emitted; a single-type import of the same simple name: nothing (the import's own hint already gives that edge); an inherited member type of a supertype the file names: the group first offers `<Super>+<Name>` for each such supertype (binds when the supertype is in the repository and declares it), then the same-package key; a local variable, parameter or field of the file with that name in an expression position: nothing (§6.4.2 obscuring). Same-package wins over on-demand imports and `java.lang`, as in Java.

**Source sets** (R4, `resolver.mts`, the JVM route only). For a same-package hint from a file under `src/main/`, definers under a sibling non-main source set (`src/test/`, `src/testFixtures/`, `src/integrationTest/`, `src/it/`, `src/jmh/`) of the same module are dropped, because main code cannot see test classes; a file of a non-main set sees its own set and `main`. Outside the `src/<set>/` layout every definer of the package counts.

**The known limit**, documented with a case: an inherited member type of a supertype outside the repository, named like a type of the same package that lives in another owner, gives a false edge. It needs a name collision across a library boundary and a split owner; the corpus (spring-petclinic, moshi, jsoup, javapoet) shows whether it occurs.

**Yggdrasil's `Before you upgrade`** (Y5, one consolidated entry with the other new edges): "**Java and Kotlin tests that use classes of their own package are now seen as dependencies.** A test in the same package as the class it tests needs no import, so `yg check` did not see it. It does now: if your graph keeps tests and main code in separate components (the Maven and Gradle `src/test` and `src/main` layout) without a relation from the tests to the code they test, `yg check` reports each such use as an undeclared dependency after the upgrade. Declare the relation (`uses`) from the test component to the component it tests." (Kotlin only if D2 = yes.) **Grain** (G9) deletes its own binding and gets these edges from Runes; spring-petclinic's proposal then declares the test → main relations and `yg check` confirms them.

## 11. Risks

- **R1 touches every resolver's I/O.** A missed disk read silently bypasses the view. Mitigation: a test that the disk view is never called when a listed view is given (a throwing disk spy), the catalogue twice, a zero-change corpus run.
- **C# reach losing real edges.** MSBuild has many ways to reference an assembly; every unknown fails open, and the acceptance is jellyfin, eShop and CleanArchitecture with no real edge lost. A Unity or other layout whose project files are not committed gets no filter (1.0.1 behaviour).
- **Java same-package edges turning Maven/Gradle graphs red.** Intended, behind `Before you upgrade`; the residual false edge is documented. Grain's proposals must declare the new relations the same day (G9 lands with Y5).
- **The pickup depends on the owner's word** (D1). Ask early; while he is away the loop does everything up to RF and stops only at the push.
- **Yggdrasil coverage margin** 91.25% branches: Y3 and Y5 are large; each reports done only at 90.2% or more on the merged hook.
- **Grain history re-keying** (G3, G5) changes replay; the incremental-equals-cold test and click/express evidence guard it; HIST_V forces a re-walk anyway.
- **Hook refresh** (G2) adds a background process to a hook; the lock, the pid and issue 199's orphan lesson are its tests.
- **225's semantics** reach owners, coverage, subjects and the portal; surface-truth must stay green (docs, knowledge topics and `--help` say the same thing).
- **226's trust root** is only as strong as the protection of the workflow file; the docs must say so rather than oversell it.
- **The corpus** is new machinery that could become a slow, flaky gate. It runs outside every `npm test`, fetches by full SHA, skips (never passes) a missing toolchain, and its heavy tier never blocks routinely.
- **Load.** Six workers at most, `nice -n 15`, one corpus run at a time; the laptop has hit full load in this loop.
- **The scratchpad repros are gone.** Every acceptance re-derives its repro from the issue text; reviewers do the same.
