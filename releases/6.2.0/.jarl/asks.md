- **a-33** (answered) · charter · issue 493 · Runes 1.1.0, issue 493 (C#). Inside a class, a name such as User in User.FindFirst("sub") can be a member the class inherits rather than a type; C# then reads the member and the code does not depend on a domain type called User. Where the base class is in the repository, Runes can tell exactly, and the acceptance of 493 now covers that. Where the chain of base classes leaves the repository (ASP.NET Core's ControllerBase, EF Core's DbContext, any package), Runes cannot see the base's members and cannot tell. Today it reads the name as a type, which gives a false edge from every ASP.NET controller that writes User.… to the node that declares a domain User (the audit's probe p42). The same choice decides the twin cases of 494 (a nested type of an outside base) and 498 (an instance method of an outside base, which hides an extension method of that name). Which behaviour should 1.1.0 ship? (a) No edge for any name that could be a member of an outside base: no false edge, but every static call and enum value inside such a class is lost too; a cruder form of this rule lost 2176 references in jellyfin, 50 in CleanArchitecture and 41 in eShop, mostly true ones. (b) Keep reading such a name as a type, as today, and document the false edge as a known limit: no true edge lost, the controller false edge stays, though at node level it is often hidden because a controller usually depends on the domain node anyway. (c) A short, hand-kept list of the public members of the most common outside bases (ASP.NET Core ControllerBase, Controller, PageModel, ComponentBase; EF Core DbContext): those names are read as members in classes derived from them, as C# reads them, and everything else as in (b); it removes the common false edge without losing true ones, at the cost of a list that must follow those frameworks and covers no others. Recommended: (c).
