## What
Minor: Runes: a tsconfig that leaves module or moduleResolution unset (or sets module commonjs alone) keeps the first-target reading of exports, where TypeScript 6.0.3 resolves it as bundler: with an exports entry listing import before require, a .cts or .cjs file, an import x = require() and a require() call bind the import target and the compiler the require target (63 of 180 compared rows for {} and for module esnext alone, 141 of 180 for module commonjs alone). It existed before 491 and 526, which do not name it.

## Acceptance

## Changelog


- a `tsconfig.json` that leaves `module` or `moduleResolution` unset is read with TypeScript 6's defaults (`module` from `target`, Bundler unless `module` says otherwise), so a `require()` call, an `import x = require()` and a `.cts` or `.cjs` file bind the `require` branch of a package's `exports`, and an import whose branch names no file binds nothing. A consumer's graph can lose a relation that named the wrong branch and gain one for the right branch.
- under a `tsconfig.json` that extends a preset the consumer's file view does not hold (`@tsconfig/node20`, installed under `node_modules`), a package's `exports` are read as the compiler reads them wherever the config, the file kind or the call form decides: a `require()` call, an `import x = require()` and an import outside an `import()` in a `.cts` or `.cjs` file bind `require`, a `.mts` or `.mjs` file binds `import`, a config that sets a Node `module` or `moduleResolution` is read under a Node resolution and one that sets `commonjs`, an ES kind or `preserve` under Bundler. Where the preset alone decides, the import binds the first listed target that a possible reading names. `moduleResolution` `bundler` beside a Node `module` is read as the compiler reads it. A consumer's graph can lose a relation that named the wrong branch and gain one for the right branch.
