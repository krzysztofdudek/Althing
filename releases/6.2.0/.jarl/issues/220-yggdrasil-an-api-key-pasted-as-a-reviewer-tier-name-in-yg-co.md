## Changelog
- Security: An API key written as a reviewer tier name, as reviewer.default, as a rule's reviewer.tier: or as a mapping key in the configuration is no longer printed in full. Every message that quotes such a value shows only its first four characters, wherever the key sits in the text (also inside a longer name, and in yg aspects, yg aspects --json and the event stream), and also for the keys of the OpenAI-compatible hosts that start with gsk_, xai- or hf_. A key committed in yg-config.yaml therefore does not reappear in terminal output, reports or --json, and a misspelled key in a key-named tier's config: no longer makes the error print it.
- Before you upgrade: yg check refuses a reviewer tier named like an API key, in yg-config.yaml and in yg-secrets.yaml. A tier name that holds a provider key (a sk-, sk-ant-, sk-proj-, AIza, ghp_, gho_, ghu_, ghs_, github_pat_, gsk_, xai- or hf_ prefix, then at least twenty key characters of which at least one is a digit or a capital letter), alone or inside a longer name (a sk-, xai- or hf_ key counts when it starts the name or follows a dash, an underscore or another separator), now fails with config-tier-name-invalid, showing only its first four characters. Such a name used to load when it was 63 characters or fewer, and the key then appeared in full in later messages. A reviewer.default shaped like a key fails with config-default-tier-unknown, also masked. A plain name you chose is refused too if it has a key prefix and a long tail with a digit or a capital letter in it; a name of lowercase letters and dashes only still loads. To clear it, rename the tier to a plain name and every reviewer.tier: in your rules that names it; if the name was a key, move the key to yg-secrets.yaml (as the tier's config.api_key) and rotate it, since a key in the committed file has already been exposed.
