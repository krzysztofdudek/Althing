Back from deferred (ruling jarl-6-2-0-scope-revised): 246 and 247 trade contents (the design research/2026-10-08-jarl-field-report-and-repository-names/design.md, A.2 and A.4), and 247 becomes the repositories entity, which its title already names; "finding moved ones" is now the root-commit check, which finds a wrong or moved checkout and names the fix. Today Repo holds a path relative to the loop root (repoOf, jarl-lib.mjs:2203-2208 at 2c12aa3). A path says where, not which: any repository at ../../../Grain is read as Grain, and nothing checks that it is one. It encodes the depth of the loop and the sibling layout (the loop survived its move only because the new directory sits at the same depth, ruling althing-move). A worktree path passes as a repository of its own. The Worktree field and the lease lines record an absolute path that belongs to one machine (:1213). And the base is whatever the checkout has checked out (defaultBase, :2231), read by check, queue, tips and branches. The principle: the record holds identity, the machine holds location, and Jarl checks one against the other, and never guesses. A sibling repository is named by the directory git clone gives it, which is its name on its host and already every Files prefix (the registry keys are not used: Jarl cannot read the Althing registry). Jarl declares it once, by itself, in .jarl/repos.md, with its root commits (all of them), its origin as found and its base branch, and no path; a name resolves to the sibling of the main checkout of the loop; a repository that is not a sibling keeps a path, as today; a machine laid out differently puts a symlink beside the checkout of the loop, and Jarl needs no code for it. The record holds no worktree location: a lease is its Branch, Worker and Since, and git allows a branch in at most one worktree, so views ask git. Dropped by the ruling: discovering moved repositories among siblings, and checking that declared files exist on the branch of the loop. ## Why
A fragile detail repeated in hundreds of issues: a wrong checkout is read as the right repository with nothing to catch it, a moved loop breaks every path, and a record that is public carries one machine's home directory and user name. With names and identity, every role finds the real checkout and worktree through the calls it already makes, on the machine where it runs, and the record holds nothing that belongs to a machine.

## Acceptance
- A repository an issue names is declared by Jarl, once, in .jarl/repos.md (name, roots, origin, base) with a log line, holding no path; repo --base <name> <branch> changes a base with a log line; repo logs every change. An issue with no Repo is read exactly as today, in the root of the loop
- Resolution lives in the one repository resolver of 325 and nowhere else: a name resolves to <parent of the main checkout of the loop>/<name>, the main checkout found through the git common directory by the one worktree-list parser of 325, so a loop opened in a linked worktree finds its siblings beside the main checkout; seams.test.mjs stays green and grep -c "reposNamed(i).length" skills/jarl/scripts/jarl-lib.mjs still prints at most 1
- The root commits are checked by verify only: verify reports a declared repository whose roots do not match, an unverified state for a shallow checkout, and a note (never a finding) for a different origin; no other command reads the roots. A name that does not resolve on this machine is shown with its fix (put the checkout, or a symlink to it, at <parent>/<name>), refused by the commands that act on it, and marked by the views
- --repo takes a name, a checkout, a worktree or a file inside a repository, reduced to its main checkout through the git common directory. It stores the name where the checkout sits at the place of the convention, and the path otherwise, with a stderr note saying why (so two repositories sharing a directory name stay apart). The format of the loop decides how a value is read: in format 1 every value is a path; in format 2 a value starting with . or / (or a drive letter) is a path and anything else a name. The first write of a name raises the format first, under the same lock, rewriting any bare-word path as ./<word>, and the pinned frozen earlier reader refuses list and status on that loop, tested. The merged-in part follows Repo; the Files prefix rule and the rule for a repository holding a directory of its own name stay as they are
- No worktree location is recorded: a new lease stores no Worktree field and its lease line no worktree path. Views read the worktree of the branch of a lease through the one worktree lookup (here; listed but not visible from here; elsewhere, locked with a reason; no worktree holds the branch), in each repository the issue names. In the CLI and the MCP tool, set --worktree checks the path (when it exists, it must be a worktree of one of the repositories of the issue with the branch of the lease checked out, or the call is refused) and stores nothing. The record library (record.mjs setStatus) stays tolerant: a worktree opts key a composer passes (Horde does) is accepted and not stored, with no refusal and no change to the jarl-record/1 contract. A lease that holds a Worktree field keeps it and is read as today until it ends; the done gate is untouched
- show, show --json (as where) and status --by repo print where each repository and the worktree of the lease are on this machine, on stdout only; status --by repo also prints the base of each repository and whether its checkout is on it (a warning only); nothing resolved is written
- Tests: a loop over two sibling repositories gets names, and keeps a path for a third that is not a sibling; a symlink beside the checkout of the loop resolves a name; verify reports a checkout of another repository under the right name by its roots; a fork with another origin gets a note, and a shallow clone reads unverified; a loop opened in a linked worktree resolves its siblings beside the main checkout; the worktree of a lease is found by its branch, including one git lists as prunable; set --worktree through the CLI refuses a wrong path while record.setStatus with a worktree key does not; the real loop through JARL_LIVE_LOOP when it is set
- Not here: a per-machine override file (kept out by jarl-6-2-0-scope-revised), a migration command, discovery of moved repositories, per-file existence checks, and a root-commit check in any command other than verify
