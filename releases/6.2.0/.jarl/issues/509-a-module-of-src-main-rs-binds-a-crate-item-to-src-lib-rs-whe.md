## What
A file under src/ gets root files [src/lib.rs, src/main.rs] in that order, and resolveFromModuleDir binds the first root that declares the item. So a module that only src/main.rs declares binds crate::X to the library root whenever the library has an X too (p46, p54). A [[bin]] with a path in src/, such as src/cli.rs, is a crate root as well, but a module it declares still gets the same two root files, so crate::X never binds that binary (p06). Rust resolves crate to the root of the current crate. Both already exist in v1.0.0. The fix picks the root by the module chain: the root file that declares the first module segment of the importing file. Issue 510 was merged into this one.

## Changelog


- In a package that has both `src/lib.rs` and `src/main.rs`, or a `[[bin]]` with a path in `src/`, `crate::Item` in a module binds the crate root that a chain of plain `mod` declarations leads to, when that root holds the item: the binary root for a module that `src/main.rs` or that binary declares, the library root for one that `src/lib.rs` declares. A module that two roots declare this way gives no edge to a root item, so a graph can show new gaps there.
- The chain is read from parse trees: each `mod x;`, also inside inline modules, from a root down to the module's file. A `mod` with a `path` attribute, a `cfg_attr` or an attribute macro on it, one written by a macro or pulled in by `include!`, and one in a file that does not parse to the end are not followed. Where no chain reaches a file, or the root it reaches does not hold the item, the roots are tried in the order of 1.0.0, the library first, so those edges stay as they were. The chain needs the pass's symbol table, which `makeResolver` passes; a caller without one gets the order of 1.0.0 for every file.
- A `mod` under a `cfg` (on the `mod`, on an inline module around it, or at the head of its file) may be removed, and whether its predicate holds is not read. Such a declaration puts its root ahead of the roots that do not declare the module and after a root that declares it without a `cfg`. It never makes a module one that two roots declare, so `#[cfg(feature = "x")] mod a;` in one root beside `mod a;` in the other keeps the edge to the root that declares it plainly.
- A module of a `[[bin]]` in `src/` reads a bare `use` path in that binary's edition: in an edition 2015 binary of a later-edition package `use foo::Bar;` binds the module `foo` the binary declares, and in a later-edition binary of an edition 2015 package it names a crate, unless the library or `src/main.rs` declares a module of that name, which keeps the edge it had. A module of the library keeps the edition it had.
