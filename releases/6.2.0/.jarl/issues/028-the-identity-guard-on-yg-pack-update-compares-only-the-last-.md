Forcing the host into the identity itself would rename packages/<owner>/<repo>/ and every rule name (a breaking change). ## Why
docs/packages.md:104-107 promises a refusal when the recorded source 'now says it belongs to someone else'; a change of owner and a change of host are equally visible in the diff, and only the first is refused, so a typo in the host (e.g. githab.com/acme/law) passes. After the swap, `yg pack verify` even vouches for the new code, and the payload is check.mjs, run in-process on every fill. The attack needs a committed change to yg-packages.yaml, which the docs (packages.md:630-636) say to review like code anyway, hence minor.

## Acceptance
- Installation records a normalised publisher (host plus the full repo path, with the ssh, https and scp forms of the same host equal); update compares it and refuses on a change of host or parent group; an e2e test next to R2 for both cases.
- Two different repositories with the same <owner>/<repo> tail do not land in one directory packages/<owner>/<repo>/ without a refusal, and docs/packages.md:91-93 describes the real reach of 'a fork cannot claim the original's rule names'.

## Changelog
- Fixed: yg pack update refuses a source moved to another host or another group with the same <owner>/<repo>, or to a plain directory when the record names an address; the record keeps the whole address a package was installed from (publisher:), and a record an earlier release wrote has it read off its recorded source by yg pack add and written in by the next yg pack update, pinned or not and even when nothing newer is published. yg pack add refuses a second repository whose address ends in the same <owner>/<repo> as an installed one's. A package that really moved to another host or group keeps its rules and adaptations when publisher: is set to the new address in the same change as source:; the refusals, yg pack verify and yg pack list say so. A local checkout's address is read as written in its git config, so a machine's url.<base>.insteadOf rewrite no longer makes an unchanged record fail. yg pack list says when a recorded source no longer matches the address a package was installed from, and yg pack verify says only that the source moved and what to do instead of vouching for what it holds; once yg pack list has reached the moved source, yg advise stops suggesting an update the command refuses. yg pack add --as with an owner like .staging-x says why it is refused.
- Before you upgrade: a package whose recorded source (source: in .yggdrasil/yg-packages.yaml) names another host, another group or a plain directory instead of the repository its publisher: names now fails yg pack verify and is refused by yg pack update. If the package really moved to another host or group and is still the same <owner>/<repo>, set publisher: in the same change as source: (it keeps its rules and adaptations, and yg pack verify confirms the copy); if it became another repository or a plain directory, run yg pack remove <name> (it refuses while a rule of it is attached) and install it again; otherwise restore source: from version control. A record an earlier release wrote has no publisher: and is not affected until an update writes it in.
