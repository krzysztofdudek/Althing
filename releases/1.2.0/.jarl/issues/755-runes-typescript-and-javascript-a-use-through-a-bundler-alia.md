## What
Claim: At v1.1.0 the readers resolve tsconfig and jsconfig paths, baseUrl, and package exports and imports. An alias that only a bundler configuration defines is not read, and explainTsMiss answers outside for the bare specifier. A repository with such an alias and no matching tsconfig paths entry has every use through it answered {"kind":"absent","reason":"outside"}, while the same use as a relative path resolves and the same alias as a tsconfig paths entry resolves.

repros.sh alias_vite: "@/data/d" and "~data/d" printed {"kind":"absent","reason":"outside"}, "../data/d" printed resolved to src/data/d.ts; alias_webpack: require("data-alias/d") printed outside; alias_babel: "@d/d" printed outside; alias_tsconfig: "@/data/d" printed resolved to src/data/d.ts

Moved from issue 755 of the 6.2.0 loop, where it stays deferred: the owner's answer to a-41 and a-42 there sends the items moved out of Runes 1.1.0 and the reader gaps 752 to 765 to the next Runes version.

## Why
A consumer that stays quiet about an outside use reports nothing for every import through a Vite, webpack or Babel alias, with no sign that a reader did not look: a Vue or Vite project that keeps its alias only in the bundler configuration passes a layer check on every such use. A new family tool that uses the readers as they are found it.

## Acceptance
- [read] A ruling in the loop says which of the two answers the readers give for a bare specifier in a repository that holds a bundler configuration: the alias read from the configuration's literals, or reason unfollowed
- [test] In a repository with a Vite resolve.alias, a webpack resolve.alias and a Babel module-resolver alias, none of them in a tsconfig, classifyUse of a use through each gives the answer the ruling picks, in a unit test and a catalogue case per bundler, red at v1.1.0 (outside) and green after; a specifier of an installed package in the same repository still gives outside, and every existing answer and edge stays as it is · by: npm run check

## Changelog
- TypeScript and JavaScript: an import through an alias that only the bundler configuration defines (Vite `resolve.alias`, webpack `resolve.alias`, Babel module-resolver `alias`, such as create-vue's `'@': fileURLToPath(new URL('./src', import.meta.url))` or `path.resolve(__dirname, 'src')`) now gives an edge to the file it names; in 1.1.0 it was read as an installed package and `classifyUse` answered `outside`. The configuration is read as text and never run: a replacement written in another form (a variable, a template, a relative string in Vite or webpack) is not followed. Where such an alias may apply, a bare specifier that names no dependency of a package.json at or above the file and no Node built-in is answered `unfollowed` instead of `outside`, and so it is where the configuration is composed from another file, whether or not it writes an alias (`export default base`, `mergeConfig(base, …)`, webpack-merge's `merge(common, …)`, `{ ...require('./babel.shared') }`, an `extends`). This can show new findings: a consumer's graph can show new edges through bundler aliases, and a consumer that reports unfollowed uses can see new ones in a repository whose bundler configuration computes its aliases or is composed from another file.

### Notes

Assumed: the configurations read are those of the nearest directory at or above the file that holds any of the listed names, all of them together; two that map one specifier to different places give no edge (unknown). vitest.config.*, vue.config.js and Nuxt or Vue CLI built-in aliases are not read (not in the plan's list).

Assumed: Vite and webpack resolve a relative string replacement ('./src') from the importing file, not from the configuration (Vite docs: relative alias values are used as-is), so the reader refuses it instead of reading it from the configuration's directory as the plan's hypothesis said; Babel's module-resolver reads it from its working directory, the configuration's, and that form is read. A bare string is a package request. path.resolve/path.join accept one or more string literals after __dirname; a top-level const holding a listed form ('@': pathSrc in skywalking-booster-ui) is not followed.

Assumed: under an alias the reader cannot follow, a bare specifier still falls through to the packages of the repository for resolution (no existing edge moves), and only the explanation changes: unfollowed unless a package.json at or above the file declares it in any dependency field or it is a Node built-in. An unreadable bundler configuration sends no config-unreadable diagnostic: that code's promise names JSON files that do not parse.

Assumed: an object member that cannot replace a key the lookup reads (a shorthand of another name, such as plugins or extensions) leaves the object readable; a shorthand in an alias object is a key with an unknown value. A directory whose configurations hold more than 64 alias lists is read as unknown (every bare specifier there unfollowed unless declared or built in). Correction of my earlier note: module-resolver reads a relative alias from its working directory (process.cwd() by default), which the reader takes to be the configuration's directory, where Babel runs.

Assumed: a spread in resolve or the configuration object is readable only where every key the lookup reads follows it (resolve for webpack, plugins for Babel, both resolve and test for Vite, since a test.alias from the spread applies too); a spread in the alias object or in module-resolver's options stays unknown. Code that changes the configuration after its object is written is named as a known limit in docs/api.md, not refused.

Assumed: the configuration is what the file exports (export default, module.exports =, export =, or the whole text of a JSON configuration), read through an object literal, an array of them, defineConfig of one argument, a function whose every return or expression body is one (a function only as the export, an exported array's element or defineConfig's argument, where the bundlers call it), and a name declared once with one, in the returning function or at the top level, and assigned nowhere in the file; parentheses and a TypeScript as or satisfies are passed over. Any other export (an imported name, a merge, any other call, a require, a member, a condition), two exports, or none leaves the file unknown, and a text with no tokens has no alias. A wrapper call that round 2 read through its literal and named a known limit (withPlugins(literal), merge(literal, ...), mergeConfig(literal, overrides)) now reads unknown.

Assumed: for each configuration object, whether or not it writes an alias, the keys the lookup reads are resolve and test (Vite), resolve (webpack) and plugins (Babel); a spread they do not follow, one of them that is no literal (written there or bound by such a name), a spread in resolve or test that alias does not follow, a spread in Babel's plugins, or an extends (webpack, Babel) leaves every bare specifier unknown. A Babel plugins array followed by .filter(...) is the array, since a filter only drops plugins. Babel presets and Vite plugins that add an alias of their own are named as a limit in docs/api.md, not read; other keys whose unread value could hide an alias the reader refuses where it sees it (webpack module, Babel overrides and env) are not checked.
