# Yggdrasil 6.1.0: documentation consistency audit

## 1. Verdict

The mechanical facts in the documentation hold up. Across README, docs/*.md, the knowledge topics, the prime template and live `--help`, these all agree: schema ids, lock and state file names, the portal port, numeric defaults, exit codes, knowledge and schema topic names, every documented flag, the sidebar (no orphan pages), and the showcase numbers. The problems are in three places. First, the packages story: packages.md describes an identity model and a drill workflow that the code does not implement. Second, the first-run path: a committed fresh `yg init` cannot be cloned and used, and interactive init echoes an API key the docs say is only read from the environment. Third, the same fact is written by hand in several places, and the copies drift: the prime manual, the docs site, the knowledge topics and the output samples. One blocker and four majors survived verification. Most of them are code defects that the documented path exposes, not wording problems. The terminology findings are real but only cause friction; their root cause is that there is no glossary. A green docs build and a green `docs-internal-links` rule do not currently show that the docs are consistent: anchors are unchecked, output samples are not snapshotted, and duplicated lists are not generated from one source.

## 2. Cross-cutting themes

- **Hand-copied facts drift between surfaces.** The same fact is typed out in prime, a docs page, a knowledge topic and a code comment, and the copies have diverged. This covers the port-baseline clause (m1), the claude-code default model (m2), the gitignore list (m8), output samples (m7) and example config comments (m15). In m2 the knowledge topic was reconciled and the site was not. In m1 the knowledge topic dropped the stale clause and prime and two pages kept it. The fix is structural: generate these from source constants, or add tests that compare the copies.
- **The packages docs describe a model the code does not implement.** Side-by-side identity (M2), drilling parameterized rules (M3), all-or-nothing update semantics (m5), and adaptation stubs and messages that point at copied files (m12). packages.md is the least trustworthy page in this release.
- **The documented first-run path breaks in ways the docs do not mention.** Clone after the first commit (B1), interactive key entry (M1), a keyless adopter losing `yg context` after the first judgment rule (m11), the README core loop and uninstall answer (m6), and stale first-check output (m7).
- **Removed features are still described as current.** The port-contract baseline, removed in 6.0.0 (m1), and `yg-review/1`, removed in this release but "newly registered" in the same CHANGELOG (m4). This is distinct from the in-flight `yg verdict` cleanup.
- **The guards report green while the docs are wrong.** `docs-internal-links` strips fragments, so broken anchors pass (m9). `yg marketplace check` says "Ready to publish" while the scaffold's own drill cases cannot run (M3). No test snapshots output samples (m7) or compares gitignore lists (m8).
- **The vocabulary for judging and coverage is overloaded and there is no glossary.** "reviewer" (m19), "approve/verified" (m20), "covered" (m21), "tier" (m22), type-covered synonyms (m23), "file-level" (m24), "family/law" (m25), "drill" (m26), "status/standing" (m27), attach channels (m28), and README rule/aspect words (m30). All of these follow from m29, the missing glossary.

## 4. Details: blocker and majors

### B1 — A committed fresh `yg init` cannot be cloned and used

- **Evidence:** `yg init --no-reviewer` creates empty `.yggdrasil/model`, `aspects` and `flows` directories. Git does not track empty directories, so after `git add -A; commit; git clone` the clone has only `.gitignore`, `yg-architecture.yaml` and `yg-config.yaml`. In the clone, `yg check` and `yg check --approve --only-deterministic` both exit 1 with "No .yggdrasil/ directory found ... Run 'yg init'". `yg init --no-reviewer` refuses ("already has a .yggdrasil/ graph"). Bare `yg init` without a TTY says there is nothing to do. `yg init --upgrade` says "Agent rules already up to date" and does not recreate model/. The cause is graph-loader.ts:180-182, which throws "Directory .yggdrasil/model/ does not exist", and preamble.ts:106-110, which rewrites any "does not exist" message into the no-.yggdrasil text.
- **Impact:** An adopter who follows README or getting-started, commits right after init and wires the documented CI step before writing a first node gets red CI. The error message names a remedy that then refuses. Every teammate clone hits the same thing. This is the first path the docs recommend.
- **Fix:** Have init write a placeholder into each directory. Have the loader treat a missing model/ as an empty graph, or at least report it with its own message that mentions git and empty directories. Stop collapsing every "does not exist" error into "run yg init". Add an e2e test covering init, commit, clone and check.
- **Verifier note:** Reproduced independently in $TMPDIR/verify-examples-run-01. Every documented repair either refuses or leaves the error in place. Not on the in-flight list.

### M1 — Interactive init echoes the API key; the docs say the key comes only from the environment

- **Evidence:** getting-started.md:35-38 says the API providers "need a key, read only from an environment variable ... never a flag". Spot-checked on release/6.1.0: the interactive flow calls `apiKey = await promptApiKey(provider)` unconditionally (init-reviewer-setup.ts:207, and again after a 401 at :222). `promptApiKey` uses `p.text` (echoed input) with `validate: (v) => ((v ?? '').trim().length === 0 ? 'API key cannot be empty' : undefined)`, even though its hint reads "(or set ${envVar} env var)". Only the non-interactive `--provider` path (:407-411) reads `process.env`.
- **Impact:** On the default path, the secret is shown on screen and in any recording or pairing session. The user must type it even with the variable already exported. The docs' env-only statements (getting-started, cli-reference.md:1658, knowledge cli-reference) are true only for `--provider`.
- **Fix:** Check the env var first. Prompt only when it is missing, and use `p.password`. Allow an empty answer when the variable is set. If the prompt is kept, rewrite getting-started.md:35-38 to say the key is asked for and stored in yg-secrets.yaml.
- **Verifier note:** Confirmed in source, not exercised in a real TTY (see §6). The in-flight init item covers `--provider` probing and comment stripping only.

### M2 — Package identity: the same name from two repositories is refused

- **Evidence:** packages.md:55-57 says "the same package name from two different repositories installs side by side and neither can claim the other's rules". Spot-checked: pack.ts:621 checks `lock.packages[spec.name]`, the bare name, before `resolveIdentity` runs at :634. Live, `yg pack add ../mkt#alpha --as acme/law` succeeds. The second install, `--as other/law`, is refused with "'alpha' is already installed ... Installing again would overwrite the copy that is there". yg-packages.yaml keys entries by bare name, and update and remove accept only the bare name.
- **Impact:** The identity model that packages.md, `--as` and the refusal table rely on does not exist. The refusal text is also wrong: the second copy would land in a different directory.
- **Fix:** Key records by `<owner>/<repo>/<package>` and accept qualified names in update, remove and list. Otherwise remove the side-by-side promise and state that package names are unique per consuming repo.
- **Verifier note:** Reproduced in $TMPDIR/verify-examples-run-02. Adjacent to the separate package-system review (issues 163-172) and should be cross-checked against those before filing.

### M3 — Parameterized package rules cannot pass their own drills

- **Evidence:** `yg marketplace init` then `yg pack new alpha`, install, then `yg drill --aspect packages/acme/law/alpha/example` gives "0 pass ... 2 unrun" ("source parse or runtime error") and exit 2. `yg aspect-test --aspect ... --files src/orders/o.ts` fails with "TypeError: Cannot read properties of undefined (reading 'example')" and "Fix the bug in check.mjs", a copied file the adopter may not edit. The same rule through `--node` passes. The scaffold's check.mjs reads `ctx.config.example` and iterates `ctx.subject`. `yg marketplace check` still reports "Ready to publish".
- **Impact:** packages.md calls `ctx.config` "the only way" to parameterize a deterministic rule. `marketplace check` requires drill cases. The docs tell authors to install the package and watch `yg drill` pass. Every parameterized rule fails that step, starting with the one the tool generates.
- **Fix:** Supply resolved config (package defaults plus adaptation) on the ad-hoc paths. Treat `ctx.subject` like `ctx.files` there. Make the scaffold iterate `ctx.files`. Add an e2e test that scaffolds, installs and drills green.
- **Verifier note:** Reproduced. Likely overlaps issue 171 ("yg drill does not run rules that read ctx.config", translated from Polish), filed today from the package review. If so, list it as corroboration rather than a new issue. The documentation side (packages.md:373-377, cli-reference.md:1854) still needs to change with the code fix.

### M4 — aspect-status.md presents attach-site status as an override; it can only raise

- **Evidence:** aspect-status.md:90-92 says "The aspect-level default applies wherever the aspect attaches unless an attach site declares its own." On a copy of examples/checkout-flow, a flow attaching `{id: emits-telemetry, status: advisory}` to an aspect with no status (default enforced) produces three aspect-status-downgrade errors: "Node 'cart' attaches aspect 'emits-telemetry' with status 'advisory', but the aspect cascades onto this node with status 'enforced' from flow:checkout." The node attaches nothing, and the flow is the site that says advisory. The error clears only when `status: draft` is added to the aspect itself. aspect-status.md:159-161 mentions the max rule "plus the aspect-level default", so the page contradicts itself.
- **Impact:** The copy-paste example gives a blocking error. The error blames a node that attaches nothing and names the advisory flow as the source of "enforced". Adopters come away with the wrong model of how status resolves.
- **Fix:** Rewrite 90-92 to say an attach site can only raise the effective status above the aspect default. Change the flow example to a promotion, or give the aspect a lower default. Make the downgrade message name the declaring site and "aspect default" as the source.
- **Verifier note:** Reproduced in $TMPDIR/verify-examples-run-05.

- Every documented `yg <cmd> --flag` exists in live `--help`. The only unlisted flag, `--attention-dump`, is hidden on purpose.
- All 21 non-home pages are in the sidebar, so there are no orphans. Every page link and public asset resolves. The GitHub links to scripts/*.mjs exist. Every `yg knowledge read` / `yg schemas read` topic named in the docs exists. The VitePress build passes.
- The showcase numbers (38 types, 33 with defaults, 12 log_required, 9 `when:` aspects, 18 flows, 4 implies chains) match the dogfood graph exactly.
- Most runnable examples work as documented: the yaml snippets assembled into one graph, the async-fs and graph-aware check.mjs examples, adopt, progressive mode including a shallow clone, the check output flags, advise, incident, suppressions, type-suggest, and all seven examples/ from a clean archive.
- The core nouns (node, flow, port, relation, mapping, lock) are used consistently.

- The knowledge topic for configuration already carries the correct reconciling text for m1 and m2. The fix is to port it, not to write it.

## 6. Completeness critique

- **No real TTY run.** Interactive `yg init` (M1, and the reconfiguration dead end in m11) was judged from source. Close with a scripted pty run (`script` or `expect`) in the container, capturing what is echoed and whether an exported env var is honoured.
- **No live LLM reviewer.** No angle made a paid or keyed reviewer call, so fresh (uncached) refusal text, judgment-rule `--approve` output, the portal's Approve path and copilot-cli/openai-compatible behaviour are unverified against the docs. Close with one keyed run over examples/failing and one judgment rule in a scratch project.
- **Family-facing pages vs sibling repos.** No angle checked family-contracts.md's producer and consumer rows against Grain and Horde source, and m4 shows the register is already wrong in the CHANGELOG. Close by grepping each registered schema id in the sibling repos on their 6.1.0 branches.
- **Knowledge topics were not diffed systematically against docs pages.** Only configuration and onboarding were compared (m1, m2, m8). Close with a test that renders every knowledge topic and checks the shared tables (config keys, gitignore, commands) against the docs pages or a single source constant.
- **CHANGELOG [Unreleased] vs code.** No angle confirmed that every Added or Fixed entry is actually implemented on the branch, or that the pending 6.0.0 to 6.1.0 bump leaves no docs saying "since 6.1.0" while `yg --version` says 6.0.0. Close with an entry-by-entry pass before the bump.
- **Help-text wording.** Flags were checked for existence, but only spot-checked for meaning (m10, m18). Close with a pass that compares each command's help description with its cli-reference section.
- **Portal glossary.js and state-model.js vs docs.** Only sampled (m19). This is the natural seed for m29 and should be diffed as a whole.
- **External links and rendered site.** Only anchors and internal links were checked. External URLs, search index and mobile rendering were not.
- **In-flight items were excluded by design.** After those branches merge, re-run the facts-and-defaults and links angles. Several of them (the CHANGELOG breaking notes, cli-reference drift) touch the same files as m4, m13 and m17.

## 7. Refuted or corrected claims

No finding was refuted outright. These parts of findings were corrected or not reproduced:

- F1 / m2: the claimed exit code 2 for `yg init --provider codex` was wrong; the command exits 1. The "adopter believes Sonnet" impact was overstated because each page is accurate for its own mechanism, so the finding was downgraded to minor.
- F3 / m8: the claim that hand-writing from the knowledge topic leaks rotated logs was overstated. The knowledge block describes what init writes, init always writes the full set, and the onboarding recipe already has the rotation globs. Downgraded to minor.
- F4 / m5: downgraded from major. Each package install is atomic and the lock stays consistent with disk.
- LSS-1 / m1: downgraded from major. Nothing writes a baseline, and a lock that still carries `ports` is refused anyway.
- EX-04 / m11: downgraded. The docs tell keyless adopters to add a judge before the first judgment rule, and the error also offers "add reviewer.tiers". The root cause is shared with the in-flight keyless abort.
- EX-07 / m12: the claimed aspect-undefined cascade was not reproduced, because no node attached the rule in the verifier's run.
- EX-09c / m7: the `.clinerules/` vs `.clinerules/yggdrasil.md` stanza difference was not reproduced live. It is plausible from init.ts:478.
- EX-12d / m15: the claim that no doc mentions the `yg portal --static` root output is wrong; portal.md:58 documents it. The uncovered-file side effect stands.
- EX-12a / m15: weak. The topic list says "include" and points to `yg knowledge list`.
- T5 / m23: miscited. The "type-level lattice" line comes from `yg tree` (tree.ts:105), not `yg check`.
- T2, T3, T8 / m20, m21, m26: the predicted harms (agents confusing `--approve` with human sign-off, mapping already-mapped files, running `yg drill` by mistake) are plausible but unobserved.
