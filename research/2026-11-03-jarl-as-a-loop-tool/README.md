# Jarl as a tool for running the work loop of one or many agents

**Question:** If Jarl is to be a tool that runs the work loop of one agent or of many, as it was meant to be from the start, what of Jarl as it stands at release/6.2.1 serves that, what is missing, what in the field report of 2026-11-03 and in the open loops serves it, and what should Jarl become?
**Method:** Read Jarl at release/6.2.1 (its skill, references and command surface), the canon's description of Jarl and Horde, the field report and its checked map (research/2026-11-03-jarl-field-report-long-loop), and the measurements of research/2026-11-03-review-granularity-and-light-models. Run thought experiments on loop shapes (one agent alone; one coordinator and many workers; several sessions and machines on one loop; a loop that is not code; a long loop across compactions with the owner away) and write down where each one breaks. The result is a design direction, which gets three independent Opus critics before anything is filed.
**Status:** open
**Conclusion:** pending

## Why this question

Krzysztof, 2026-11-03 (translated from Polish): "Think the whole of Jarl through again, with what exists, what is in the report, what could be and what makes sense. In general I would like to have from this a tool for running the work loop of one or many agents. That was the idea from the start. Tell me what comes out of this analysis."

## The owner's further input, 2026-11-03

Krzysztof (translated from Polish), on a hierarchy of agents: "Very often I have a main agent working, for example, on Opus at extra high, for thinking things through, and we work on the backlog. But often the subagents go through it, report to it that the work is done, and generally swamp it. So I started doing it mechanically on the side: a main session for governing, and an additional executor whose only job is doing the tasks in a loop. The boss, I do not know what to call it, talks with me about the concept; it thinks at a high level and is, say, Opus 5.5. Jarl is agnostic and should stay agnostic of particular models, but there are strong, medium and weak models, the weak for light tasks. So I want a strong model for thinking and for working on the backlog, a medium model for coordination, and then executors depending on the task. Ideally the one at the very top decides; let us call it the Jarl. Under it there is a coordinator, and under that, executors and reviewers. It would be ideal if this Jarl talked with me, delegated to the coordinator, and the coordinator did not bother it until it has to. The point is not to spam the Jarl with things that should not interest it."

On several coordinators: "There can be several coordinators. The Jarl decides how: if it created the backlog and there is a hierarchy in it, it should be possible to split the backlog among coordinators, for example by tag, because the tag system is universal and anything can go there. So a tag per coordinator, and each coordinator handles its part of the backlog and does not bother the Jarl until it has to. That would be a fairly ideal solution. Here we are talking about subagents, not T3 Code threads. So there would be a conceptual Jarl, coordinators as needed, executors as needed and reviewers as needed."

On routing: "A Jarl loop lives within a given area, a topic or whatever someone uses; it does not have to be in a workspace, someone may have no such workspace. I would like the skill to hold the general routing, while the tool itself, through MCP or the CLI, uses the right things. With MCP there is this problem: we work in the top directory we are in, if I am not mistaken. Is it possible to give a specific sub-area, a topic one in this case? If so, fine; the point is that the MCP communicates in the way the agent needs."

On rules with a scope (Krzysztof, 2026-11-03, translated from Polish): "What is getting through to me is that the rules we said would be a kind of law in force in the loop or for a given task should perhaps also apply to a particular tag or a particular agent role. Then it would be simpler to give rules that come up while creating the backlog, or during work or fixing, something self-correcting over time that would propagate by itself. So you could attach such a thing to various kinds of elements in Jarl: decide something at the global level, at the level of a task, of an agent's role, of a tag. What do you think? Maybe there are other criteria, and other places to attach them. I say this on purpose, because these things come up and I often have to remind the agent. It says it remembers, that it wrote it down somewhere, but unless I explicitly and bluntly write it somewhere, it gets lost: if I do not add it to the task, or to some file that has to ping the agents. That is weak; it would be better to solve it systemically." He gave it with an example from private work, distilled in the evidence of issue 058 of the 6.3.0 loop: a rule Jarl's reviewer reference already holds did not reach hand-written review briefs.

On nesting (Krzysztof, 2026-11-03, translated from Polish): "In general a subagent can run subagents; there is no problem with that." This answers the fidelity critic's Critical finding C1 for the owner's hosts: a coordinator raised by the jarl raises its own workers and reviewers. It was not verified by a run in this investigation.
